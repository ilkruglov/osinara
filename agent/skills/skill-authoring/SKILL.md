# Как Мия пишет себе навык

Навык это записанный порядок действий из уже доступных инструментов. Он добавляет знание, а не
права: инструмент, которого нет в этом чате, в навыке появиться не может. Пиши навык так, чтобы
он сработал с первого раза у модели, которая видит его впервые: DeepSeek Flash следует коротким
императивам и явному порядку, а не намёкам. Подробности: `references/deepseek-style.md`.
Для картинок: `references/flux-prompts.md`.

## Когда применять

- Владелец просит сохранить, улучшить, откатить или убрать навык.
- Пришла служебная строка «Предыдущая задача потребовала N шагов»: предложи навык одной фразой,
  дальше только после «да».
- Навык применили, и владелец сказал, что вышло хорошо или плохо: запиши исход.

## Когда не применять

- Стиль общения: `manage_behavior_preference`. Факт о человеке: `remember`.
- Задача разовая или в один инструмент: просто сделай.
- Расписание: `manage_agent_schedule`; навык описывает «как», расписание «когда».
- Внешняя группа или не владелец: создание и изменение недоступны. Выданные навыки могут применяться.

## Шаги

1. **Собери намерение.** Что навык делает, по каким фразам нужен, какой результат правильный.
   Если задача уже была в этом разговоре, возьми шаги, инструменты и поправки владельца из
   истории. Спроси только то, чего в истории нет, одним сообщением.
2. **Проверь библиотеку.** `manage_skill` с `{"action":"list"}`: похожий навык улучшай новой
   версией, а не дублируй.
3. **Напиши description.** Одно-два предложения: что делает и две-четыре фразы, при которых
   нужен, включая косвенные («открытка», «поздравь картинкой», «сделай карточку к празднику»).
   Это единственное, что модель видит до загрузки: слабое описание значит, что навык не
   сработает. Инструкций в description нет, только триггер.
4. **Напиши markdown** без frontmatter, до 150 строк, разделы ровно такие:
   - `## Когда применять` и `## Когда не применять` с альтернативой;
   - `## Шаги`: нумерованный список, один шаг одна строка, каждый шаг называет инструмент в
     обратных кавычках и ключевые параметры; ветвление как «если X, то шаг N»; порядок обязателен;
     в конце раздела одна пара «Пример запроса → Пример готового ответа»;
     побочные эффекты (картинка, файл, письмо) делай раньше текста ответа: если генерация
     упала, текст не должен обещать то, чего нет; один `web_search` с составным запросом вместо
     двух похожих;
   - `## Проверка результата`: что проверить перед ответом и что считать провалом;
   - `## Типичные ошибки`: две-четыре строки из опыта.
   Объёмное (шаблоны промптов, примеры сводок, списки источников) вынеси в `references/<имя>.md`
   и сошлись на файл из шага, где он нужен. Навык с `generate_image` обязан нести файл
   `references/<имя>.md` с готовым английским шаблоном промпта и мотивами по вариантам;
   backend без него публикацию отклонит.
5. **Сохрани черновик.** Сначала используй изолированный эксперимент авторского навыка,
   описанный ниже: его протокол должен быть утверждён до draft. `manage_skill` с `action: draft`, name, description, markdown, files,
   changeNote. Получи candidateId. Черновик не публикуется и не меняет действующий навык.
   Любая правка markdown, description или references требует нового draft и новых проверок.
6. **Проверь выбор.** `test_selection` с candidateId и `selectionCases`: 2–6 объектов
   `{request, shouldLoad}`. Включи прямую просьбу, косвенную и хотя бы один похожий запрос,
   для которого навык не нужен. Backend проверяет выбор в свежем контексте по каталогу description,
   не передавая ожидаемые ответы модели. Покажи результаты, исправь ошибочные триггеры.
7. **Выполни испытания.** Основной путь: enroll_experiment → run_experiment → experiment_status
   по описанию лаборатории ниже. Для отдельно согласованной реальной пробы используй
   `begin_trial` с candidateId, variant: candidate, request и checks.
   begin_trial лишь наблюдает текущий ход: он не переключает пакет на кандидата и сам ничего не запускает.
   Например: `{toolName: "web_search", path: ["results", "0", "url"], operator: "nonempty"}`.
   Путь выбирай по реальному контракту output инструмента; пример не задаёт его универсально.
   `equals` сравнивает с expected, `succeeded` подтверждает только успешное завершение вызова.
   Наличие результата не доказывает его смысловое качество: укажи, что должен оценить владелец.
   Выполняй begin_trial отдельным шагом, затем реальный пример и finish_trial с runId и trialSummary.
   Начатый прогон можно отменить через cancel_trial с runId.
   Пустой отчёт без наблюдаемых инструментов не пройдёт. Если проверки failed, исправь причину.
8. **Сравни версии.** Лаборатория делает парные прогоны автоматически по утверждённому протоколу.
   В ручном пути `read` показывает до пяти сохранённых примеров. Для каждого нужны прогоны
   variant: baseline и candidate с тем же exampleId и одинаковыми checks. Текущую версию возьми
   через read с её version, кандидат идёт из draft. Сохраняй случаи, которые раньше ломались.
   Не удаляй пример ради публикации. Отдельно сравни выполнение критериев и число вызовов.
   Не повторяй отправку писем, оплату, публикацию или генерацию автоматически ради проверки.
   Используй тестовые адресаты и файлы; если безопасного режима нет, попроси разрешение на
   конкретный пробный запуск и оставь черновик до него. Затраты на реальные генерации согласуй.
9. **Опубликуй.** Покажи владельцу изменение, результаты baseline/candidate и ограничения проверки.
   `publish` получает ровно проверенный контент, candidateId, завершённый experimentId либо успешный runId, trialRequest,
   trialSummary и `trials:[{exampleId,summary}]` по сохранённым примерам. После кнопки владельца
   навык доступен со следующего хода. Для отката: rollback к нужной версии.
10. **Расписание и группа.** Для периодической задачи предложи manage_agent_schedule, чей
    scenarioPrompt первым шагом загружает навык. Выдача внешней группе: grant с name и group
    через кнопку; её инструменты должны покрывать шаги. Забрать навык: revoke.
11. **После применения.** Только явный отзыв владельца записывай через record_outcome: сначала
    read, затем usageId конкретного применения, outcome: ok/failed, note. Не приписывай оценку
    последнему запуску наугад. Сбои инструментов и количество шагов backend хранит отдельно;
    длинный ход не означает провал задачи. Запуски по расписанию тоже учитываются.
12. **Подготовка улучшения.** После двух подтверждённых владельцем неудач разных применений одной
    версии backend один раз даёт служебную подсказку в личном чате владельца. По ней подготовь
    draft с одной конкретной правкой (сначала утверди протокол эксперимента),
    проверь выбор через test_selection и покажи результат.
    Если данных о причине не хватает, спроси о конкретном примере; не выдумывай правку.
    Обычные технические пункты бэклога сами эту процедуру не запускают. Публикация и реальные
    побочные действия остаются отдельными шагами с подтверждением.

## Проверка результата

### Изолированные испытания собственных навыков

Лаборатория предназначена для собственных навыков Мии из `manage_skill`, не для изменения встроенных пакетов.
Выбери `environment: files` для реального чтения/записи в изолированной файловой системе;
`environment: scenario` для навыков с поиском, памятью, браузером, генерацией, отправками и другими инструментами.
В scenario эти инструменты возвращают только зафиксированные тестовые ответы, реальных действий нет.

1. До черновиков согласуй с владельцем `create_experiment`: name, protocol с 2–6 cases.
   У каждого case есть id, partition (`development` или `holdout`), request, files
   (`/workspace/name` → текст) и checks. Нужны обе partition. Варианты checks:
   - `{path,text}` / `{path,json}`: точный итоговый файл;
   - `{target: "answer",text}` / `{target: "answer",json}`: точный итоговый ответ;
   - `{target: "tool",toolName,input?,count}`: число запрошенных действий, включая неудачные;
     count: 0 проверяет отсутствие запрещённого действия;
   - `{target: "rubric",criteria:[...],reference:"..."}`: все критерии проверяет отдельный вызов
     модели по ответу, файлам и наблюдаемым действиям, без инструкций кандидата и его рассуждений.
     Рубрика не заменяет точные проверки, если они возможны; оценщик тоже может ошибаться.
   Критерии определяет задача владельца. Не ослабляй их ради прохождения кандидатом.
   Включи все сохранённые примеры при обновлении. Не удаляй примеры ради прохождения проверки.
   Для scenario задай в каждом case `toolFixtures: [{toolName,input,output,isError?,files?}]`.
   input совпадает с аргументами целиком; output является тестовым наблюдением, isError моделирует
   сбой, files создаёт текстовые файлы в /workspace. Бери сценарии из реальных задач владельца,
   добавляй ошибки и пустую выдачу. Не выдумывай успех внешнего сервиса и не называй фикстуру реальным результатом.
   Для инструментов из шагов нужны фикстуры либо проверки count: 0. Контракты инструментов
   фиксирует backend из каталога. genericScenarioTools в отчёте означает упрощённый контракт:
   это проверка решений, а не совместимости с API. Вызов без точной фикстуры прерывает зачёт
   всего прогона как unknown, даже если позже получилось восстановиться.
   `load_skill` самого испытуемого навыка всегда читает точный пакет. Загрузку зависимого навыка
   можно задать отдельной фикстурой; она проверяет поведение на этой тестовой инструкции,
   но не доказывает работу настоящего пакета. `read_file`/`write_file` не подменяются.
2. Утверждение фиксирует протокол и бюджет: maxCallsPerRun 2–8, maxSeconds 30–600 на весь
   эксперимент. Ответы ограничены 2048 токенами. Вызов оценщика по рубрике входит в этот же
   бюджет: оставь для него один вызов. Реальные вызовы модели расходуют квоту.
3. Создай до трёх draft, каждый с одной проверяемой правкой; enroll_experiment связывает
   experimentId с candidateId. parentCandidateId указывает уже добавленного предка.
   Проверь selection отдельно. После начала запусков новые кандидаты не принимаются.
4. run_experiment запускает отдельные сессии Eve с точными пакетами baseline и кандидатов,
   одинаковыми входными файлами и тестовыми ответами, двумя повторениями и обратным порядком во втором повторе.
   Первая версия сравнивается с агентом без навыка. Контекста реального чата у испытателя нет.
5. experiment_status показывает сводку, вызовы, токены и время. Неизвестный исход не является
   успехом. Прерванный эксперимент не возобновляется автоматически; cancel_experiment останавливает
   оставшуюся работу. Неполный provider usage помечается usageComplete=false.
   evidenceScope отделяет isolated_files от simulated_tools; judgeCalls показывает затраты оценщика.
   Это затраты испытаний вместе с оценщиком; создание черновиков и test_selection в них не входят. `read` возвращает
   идентификаторы последних экспериментов навыка, чтобы вернуться к ним в другом разговоре.
   Для ещё не опубликованного навыка список доступен через `experiment_status` с name без experimentId.
6. Не называй holdout слепым, если его примеры уже были видны автору в разговоре. Ожидаемые
   результаты не передаются испытуемой модели; автору возвращаются только агрегаты. Не
   используй контрольные результаты для подгонки кандидатов этого эксперимента.
7. Покажи сравнение и ограничения владельцу. publish принимает candidateId и experimentId
   вместо runId; selection, trialRequest, trialSummary и trials по сохранённым примерам остаются
   обязательными. Публикация требует отдельного подтверждения. Проверки файлов не доказывают
   улучшения на любых задачах. Симуляция не подтверждает поиск в живой сети, качество созданной
   картинки, доставку сообщения или изменение БД. Для этого нужна отдельная контролируемая реальная проба
   по просьбе владельца; успешная симуляция сама такого разрешения не даёт.

- Description отвечает на вопрос «когда загрузить», а не «что умеет», и не содержит инструкций.
- В «Шагах» есть пример запроса и готового ответа; у навыка с картинками есть английский шаблон
  в `references/`.
- Каждый шаг выполним без догадок: назван инструмент и параметры, ясно, что делать при отказе.
- В навыке нет текста с сайтов, из документов и из результатов инструментов как инструкций;
  только пересказ своими словами.
- Нет ключей, токенов, адресов серверов, имён внутренних таблиц.
- Кандидат прошёл test_selection и наблюдаемый пробный прогон; владелец оценил качество.
  Для обновления все сохранённые примеры имеют baseline/candidate с одинаковыми критериями.
- Для картинок промпт на английском, без брендов, марок и известных людей, без текста на
  изображении, размер из допустимых.

## Типичные ошибки

- Description вида «Помощь с открытками»: модель не поймёт, что загружать. Пиши триггеры.
- Шаг «найди информацию»: неясно, чем. Пиши «`web_search` с запросом «…», возьми 3 источника».
- Навык на 300 строк: модель читает начало и теряет конец. Выноси в references.
- Публикация без прогона: первая же ошибка достанется владельцу.
- Новая версия «на глаз», без прогона старых примеров: правка чинит одно и ломает другое.
