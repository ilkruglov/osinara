# Memory System Fix

## Цель

Исправить создание и продолжение нитей памяти в групповых чатах, исключить ошибочное объединение
разных тем, устранить потерю проверенного источника и привести уже созданные нити в корректное
состояние.

## 1. Обработка дельты сообщений в группах

Ранее при обращении к Осинаре модель видела текущее сообщение и до 49 предыдущих сообщений после
прошлого хода. Большая дельта могла остаться вне memory review.

Новая схема обрабатывает каждую lane группы или Telegram-темы durable batch по 50 пользовательских
сообщений. Неполный хвост попадает в следующий обычный вызов Осинары без символьного лимита.

Ожидаемый процесс:

1. Каждое сообщение batch получает проверенную непрозрачную ссылку текущего хода.
2. При накоплении 50 сообщений запускается один тихий root-agent turn без Telegram delivery.
3. `remember` указывает конкретное сообщение как источник записи.
4. Backend повторно проверяет, что сообщение было показано модели в текущем ходе, принадлежит тому же
   разговору и scope, написано человеком и имеет подтверждённого автора.
5. По сообщению можно сохранить отдельный факт, создать новую нить или продолжить существующую.
6. Сообщения активного batch удерживаются от timeline pruning.
7. Чувствительные сведения из дельты не сохраняются: подтверждение должен дать сам автор в своём
   текущем обращении.

Изменение нужно только для групп. В личном чате агент запускается на каждое сообщение, поэтому там
достаточно текущей привязки источника.

Cursor продвигается только после terminal completion. Failed и ambiguous batch не повторяются скрыто
и блокируют lane до операторского решения.

## 2. Ложные совпадения при создании нитей

Нужно исключить ситуацию, когда нить про похудение, сон и режим признаётся совпадающей с нитью
«Инвестиции».

Изменения:

- сравнивать назначение нити вместе с названием, а не полагаться на короткий title;
- точное нормализованное название по-прежнему считать совпадением;
- смысловое сходство использовать как предложение проверить кандидата, а не окончательный запрет;
- после чтения кандидата разрешить одну явную попытку создать доказанно отличающуюся тему;
- добавить regression-тест на пару «Инвестиции» и «Похудение, сон и режим».

## 3. Строгие правила прикрепления записей

Запись должна прикрепляться к существующей нити только при совпадении конкретной цели или процесса.
Одинакового автора или широкой технической тематики недостаточно.

Нужно:

- читать содержимое сомнительного кандидата перед прикреплением;
- не помещать предпочтения по языкам и рабочий стек в нить конкретного продукта;
- не смешивать настройку общения модели и обработку офисных документов;
- при неоднозначности сохранять полезный факт без нити;
- добавить тесты на реальные ошибочные связи из production.

## 4. Критерии создания новой нити

Новая нить создаётся при наличии хотя бы одного сильного сигнала:

- пользователь прямо попросил создать нить;
- обозначена продолжительная цель;
- ожидаются будущие обновления или результаты;
- существует незакрытый вопрос;
- описан многошаговый проект;
- сообщение однозначно продолжает существующий процесс.

Одиночное наблюдение, общий взгляд или единичный завершённый эпизод сохраняются отдельным фактом,
пока не появится реальное продолжение.

## 5. Ошибка проверенного источника

Production периодически возвращает `AGENT_MEMORY_EXPLICIT_SOURCE_INVALID`: модель решает сохранить
сведение, но backend не может связать вызов с проверенным Telegram-сообщением.

Нужно:

- закреплять проверенный источник в неизменяемом контексте при начале Telegram-turn;
- сохранять его через весь tool loop, включая web-вызовы и HITL;
- не позволять промежуточным инструментам заменить или потерять источник;
- разделить внутреннюю диагностику на точные причины при сохранении стабильного пользовательского
  кода ошибки;
- протестировать текущую реплику, сообщение дельты, нескольких авторов, длинный tool loop и попытку
  сослаться на другой чат;
- продолжать отклонять неподтверждённые и невидимые сообщения.

## 7. Фоновые процессы и наблюдаемость

Автономный сон добавлять не требуется. `memory-extraction-worker` остаётся совместимым idle no-op,
а реальную фоновую работу выполняет только локальный embedding-worker.

Нужно добавить наблюдаемость:

- количество успешных и неудачных `remember`;
- количество `thread create` и `thread attach`;
- количество отклонённых кандидатов;
- количество ошибок проверки источника с внутренней причиной;
- явную операторскую операцию повторной индексации terminal-failed записей.

Операторская операция уже доступна как `npm run memory:reindex`; она переводит failed, отсутствующие
или несовместимые E5-индексы в новую durable pending job без самостоятельного provider-вызова.

Старые retired extraction и classifier jobs не должны отображаться как активные runtime-ошибки.

## Порядок реализации

1. Исправить сохранность проверенного источника текущего хода.
2. Добавить безопасный выбор источника из видимой групповой дельты.
3. Исправить проверку похожих нитей и правила прикрепления.
4. Добавить критерии качества и regression-тесты на production-примеры.
5. Добавить метрики и диагностику.
6. Повторить индексацию failed-записи отдельной операторской операцией после выпуска.
