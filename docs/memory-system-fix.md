# Memory System Fix

## Статус документа

Это черновик для обсуждения, а не утверждённый план реализации.

Ни один из описанных ниже вариантов пока не выбран. Перед разработкой нужно отдельно разобрать
ожидаемое поведение, сравнить варианты на реальных сообщениях и решить, приносит ли изменение пользу.

Ранее выполненные работы удалены из этого файла. Здесь остались только открытые вопросы, обнаруженные
после запуска фоновой проверки памяти в production.

## Наблюдения из production

Снимок от 14 августа 2026 года:

- фоновые batch по 50 пользовательских сообщений завершаются, cursor продвигается;
- `remember` проверяет источник записи и не принимает сообщение из другого хода или разговора;
- полностью одинаковый нормализованный факт усиливает существующую запись вместо создания новой;
- похожие по смыслу, но по-разному сформулированные факты могут сохраняться отдельно;
- один batch сделал 18 операций сохранения вокруг нескольких повторяющихся тем;
- часть `source_not_bound_to_turn` возникла после завершения batch, когда Eve повторно доставила старый
  workflow step, а source binding уже был штатно удалён;
- текущая диагностика не отличает отсутствующий binding от неверно выбранного `sourceSequence`.

Эти наблюдения показывают, что основной pipeline работает. Открытые вопросы относятся к качеству
памяти, понятности контракта источника и безопасной обработке повторной доставки.

## Простые понятия

### Факт памяти

Одна самостоятельная долговременная запись. Например: «Пользователь не хочет заниматься железом».

### Точный дубль

Тот же текст после приведения регистра, пробелов и пунктуации к общему виду. Такие повторы backend уже
объединяет в одну запись и сохраняет дополнительное подтверждение источником.

### Смысловой дубль

Тот же смысл другими словами. Например:

- «Пользователь не хочет заниматься железом»;
- «Пользователь предпочитает заниматься только софтом».

Сейчас такие записи могут считаться разными.

### Подтверждение существующего факта

Новое сообщение не создаёт ещё одну запись, а добавляет к существующему факту новый проверенный
источник. Это полезно, когда один и тот же факт повторяется в разное время.

### `sourceSequence`

Внутренний порядковый номер сообщения в timeline группы. Он нужен, чтобы backend мог доказать, из
какого конкретно сообщения модель взяла факт. Это не Telegram message ID и не номер reply.

### Повторная доставка

Eve может повторно запустить часть workflow после транспортного сбоя. Повтор уже завершённой операции
не должен создавать новый факт, терять результат или выдавать ложную ошибку.

## 1. Нужно ли искать похожие факты перед сохранением

### Проблема

Backend объединяет только точные дубли. `search_memories` доступен модели, но тихая проверка не обязана
вызывать его перед каждым `remember`, а существующая память не показывается ей автоматически.

### Варианты для обсуждения

1. Только усилить инструкцию: перед сохранением модель сама ищет похожие записи.
2. Backend сам находит несколько похожих кандидатов и просит модель выбрать действие.
3. Перед обработкой batch автоматически показать модели ограниченный список релевантных записей.
4. Оставить только точное объединение и принять смысловые повторы как цену безопасного поведения.

Автоматически объединять записи только по близости embedding нельзя без отдельного решения: два
похожих предложения могут описывать разные периоды, людей или решения.

### Что нужно решить

- Что считать тем же фактом, а что новой подробностью?
- Должна ли новая формулировка заменять старый текст или только добавлять источник?
- Как учитывать изменение мнения со временем?
- Должны ли совпадать человек, группа, проект и нить?
- Сколько дополнительных tool calls и model tokens допустимо тратить на одну проверку?

### Как проверить до реализации

- взять несколько реальных production batch;
- вручную отметить факты, смысловые дубли и действительно разные записи;
- прогнать каждый вариант на одинаковых данных;
- сравнить количество полезных записей, пропущенных фактов, ложных объединений, задержку и стоимость;
- отдельно проверить противоречащие друг другу факты и изменение предпочтения со временем.

Решение не принято. Требуется отдельное обсуждение результатов сравнения.

## 2. Нужно ли объединять факты внутри одного batch до записи

### Проблема

Модель может несколько раз сохранить одну тему из разных сообщений или повторить почти тот же факт
после следующего model step. История успешных `remember` доступна в ходе, но одной инструкции оказалось
недостаточно.

### Варианты для обсуждения

1. Сначала составить внутренний список кандидатов из всех 50 сообщений, затем сохранить итоговый набор.
2. Сохранять по мере чтения, но перед каждым `remember` сравнивать кандидат со всеми успешными
   сохранениями текущего хода.
3. Добавить backend-проверку похожих записей, созданных в той же session и turn.
4. Совместить предварительную консолидацию модели с backend candidate gate.

### Что нужно решить

- Нужен ли отдельный подготовительный этап модели?
- Может ли один факт ссылаться сразу на несколько сообщений batch?
- Как выбирать основной источник, если один смысл повторили несколько участников?
- Не приведёт ли консолидация к потере важных различий между авторами?

### Как проверить до реализации

- использовать batch, который создал 18 операций вокруг нескольких повторяющихся тем;
- сравнить число фактов до и после консолидации;
- вручную проверить, не исчезли ли автор, дата, уточнение или изменение мнения;
- измерить дополнительные model steps, tool calls, время и стоимость.

Решение не принято. Сначала нужен эксперимент на зафиксированном наборе сообщений.

## 3. Как сделать выбор `sourceSequence` однозначным

### Проблема

Background prompt показывает `sourceSequence` внутри каждой JSON-записи, но инструкция ссылается на
отдельный `<memory_review_source_selection>`, которого в background ходе сейчас нет. Это может путать
модель, хотя production-ошибки также могут быть вызваны повторной доставкой после завершения хода.

### Варианты для обсуждения

1. Добавить отдельный доверенный список разрешённых `sourceSequence` в background prompt.
2. Сформировать schema `remember`, которая разрешает только номера из текущего batch.
3. Заменить свободную строку на специальную непрозрачную ссылку источника.
4. Оставить текущий формат, но исправить текст инструкции и улучшить диагностику.

### Что нужно решить

- Достаточно ли модели отдельного списка, или ограничение должно находиться в tool schema?
- Нужно ли показывать все 50 значений дважды: рядом с сообщением и в trusted selection?
- Будет ли непрозрачная ссылка понятнее номера timeline?
- Как сохранить удобство interactive review и обычного группового хода?

### Как проверить до реализации

- записать реальные tool payload для успешных и отклонённых вызовов без содержимого памяти;
- отдельно считать неверный номер и отсутствие source binding;
- прогнать одинаковые batch с текущим prompt, отдельным списком и ограниченной schema;
- сравнить число исправлений модели и неудачных вызовов.

Решение не принято. Сначала нужна точная диагностика причины каждого отказа.

## 4. Что делать с повтором Eve после завершения batch

### Проблема

После terminal completion source binding удаляется. При транспортной повторной доставке Eve может снова
запустить старый `remember`. Операция уже могла успешно сохраниться, но повтор не доходит до проверки
идемпотентности и получает `source_not_bound_to_turn`.

### Варианты для обсуждения

1. До проверки source binding искать уже завершённую операцию по точному `callId` и возвращать прежний
   результат.
2. Хранить source binding дольше terminal boundary, пока Eve гарантированно не завершит возможные
   повторные доставки.
3. Исправить или локально пропатчить Eve так, чтобы settled tool action не запускался повторно.
4. Сочетать runtime-защиту Eve с replay-safe lookup приложения.

### Что нужно решить

- Где проходит правильная граница ответственности между Eve и приложением?
- Можно ли безопасно вернуть прошлый результат без повторной проверки уже удалённого источника?
- Сколько времени допустимо удерживать source rows и retention hold?
- Как поведение изменится после будущего обновления Eve?

### Как проверить до реализации

- искусственно оборвать доставку после успешного `remember`, но до подтверждения workflow step;
- повторно доставить тот же step после terminal completion;
- доказать, что memory item и side effect созданы ровно один раз;
- проверить, что другой payload с тем же `callId` отклоняется;
- проверить освобождение source rows и cursor независимо от повторной доставки.

Решение не принято. Любой вариант должен сохранить fail-closed авторизацию и exact-once side effects.

## 5. Какая память группы вообще считается полезной

### Проблема

Даже без дублей система может сохранять слишком много краткосрочных мнений, случайных реплик и сведений
о людях, которые больше не пригодятся. Большое число технически корректных записей ещё не доказывает
пользу памяти.

### Что нужно обсудить

- Какие факты о случайных участниках группы стоит сохранять?
- Нужны ли разовые планы, шутки, просмотренные фильмы и текущие подписки?
- Когда предпочтение достаточно устойчиво для памяти?
- Нужна ли разная политика для семьи и внешней группы?
- Как долго должны жить факты, которые могут быстро устареть?
- Нужно ли отдельно ограничивать число записей из одного batch или про одного человека?

### Как проверить пользу

1. Собрать набор реальных будущих вопросов к группе и её участникам.
2. Получить ответы без новой памяти, с текущей памятью и с более строгим отбором.
3. Вручную оценить полезность, точность, лишние сведения и опасные устаревшие выводы.
4. Измерить, сколько сохранённых записей реально когда-либо попало в retrieval.
5. Проверить, улучшается ли ответ достаточно, чтобы оправдать model calls, хранение и задержку.

До такого сравнения нельзя считать большее количество записей улучшением.

Решение не принято. Нужны продуктовые критерии полезности, а не только технические метрики.

## 6. Какая наблюдаемость ещё нужна

Успешные и неудачные `remember`, thread action и terminal batch уже оставляют структурированные события.
Не хватает данных, которые разделяют причины и позволяют оценивать качество.

Нужно обсудить сбор следующих показателей:

- source binding отсутствовал или модель выбрала номер вне текущего batch;
- вызов был новой операцией или replay уже завершённого `callId`;
- точный дубль усилил существующий claim;
- semantic candidate был показан модели и какое решение она приняла;
- сколько операций и отдельных memory items создал каждый batch;
- длительность batch, число model steps, tool calls и transport redelivery;
- сколько записей позже использовались retrieval и помогли ответу;
- сколько записей были исправлены, удалены или признаны устаревшими.

Содержимое памяти и сообщений в метрики и обычные логи попадать не должно.

Решение о конкретной системе метрик не принято. Сначала нужно выбрать вопросы, на которые эти данные
должны отвечать.

## 7. Что делать с уже созданными смысловыми дублями

Автоматически чистить production-память до утверждения правил нельзя. Есть риск объединить разные
факты, потерять источники или стереть изменение мнения во времени.

Варианты для будущего обсуждения:

1. Ничего не менять в старых данных, исправить только новые записи.
2. Подготовить read-only отчёт о похожих кандидатах для ручного решения владельца.
3. После утверждения правил выполнить отдельную audited cleanup-операцию с сохранением всех evidence.

Любая очистка должна быть отдельной задачей после выбора политики и проверки на копии production-данных.

## План обсуждения

1. Согласовать простыми словами, какую память считаем полезной.
2. Разметить небольшой набор реальных batch и ожидаемый итог по каждому.
3. Сравнить варианты dedupe и source contract на одинаковых данных.
4. Отдельно воспроизвести Eve redelivery после terminal completion.
5. Определить метрики пользы, ошибок, стоимости и задержки без заранее придуманных порогов.
6. Выбрать только те изменения, которые показали измеримое улучшение.
7. Написать отдельный утверждённый план реализации и только после этого менять production-код.

## Сейчас не делать

- не реализовывать semantic auto-merge;
- не менять prompt и tool schema без сравнительного теста;
- не удалять существующие записи памяти;
- не увеличивать скрытые retry;
- не ослаблять проверку источника;
- не принимать перечисленные варианты как уже согласованные решения.
